# Requirements: kritva-nexus

Register of the Nexus system requirements for task KOS-NEXUS-084 (acceptance criteria AC-010 and AC-011). Owner and reviewer: Dinesh (interim, not independent). Nexus is outside the V2 plan and not registered in kritva-program, so nothing here is a baseline commitment.

Rules:

- IDs `NX-REQ-NNN` are stable and never reused. A retired requirement becomes SUPERSEDED or WITHDRAWN and stays in the table.
- Label: `SELECTED` means the owner stated the item and a decision record in [../decisions/DECISIONS.md](../decisions/DECISIONS.md) holds it; `PROPOSED` is recommended and not approved; `OPEN` needs engineering definition. A PROPOSED or OPEN statement is not an approved commitment.
- Source wording is as relayed from the A0 integration draft discussion. The A0 draft itself is not yet in this repository, so each SELECTED label is confirmed by the owner's approval of the pull request that adds it, and any wording found to differ from the owner's original is corrected under a new addendum, not silently.
- No performance, timing, power or area value appears unless the A0 draft or the owner states it. Widths, frequencies, outstanding-transaction counts, address-map apertures and cache policies are not yet requirements.
- Verification method names the planned evidence environment (review, RTL simulation, Renode simulator, co-simulation, FPGA, OpenLane); no method has been run. Acceptance column: no per-requirement criterion exists yet; AC-010 and AC-011 govern the register itself.
- The four architecture gaps NX-ARCH-GAP-001 to 004 are carried as OPEN requirements and stay OPEN until KOS-NEXUS-006, 007 and 008 resolve them. NX-ARCH-GAP-001 is closed: NX-REQ-027 is SUPERSEDED by NX-REQ-067 to NX-REQ-075. NX-ARCH-GAP-004 is resolved by proposal (NX-REQ-030, NX-REQ-076 to NX-REQ-078). A PROPOSED item is changed by a change request: a pull request that edits it with a changelog entry; a SELECTED item also needs a new decision record.
- NX-REQ-082 to NX-REQ-091 are the RTL engineering requirements of the RTL Design Standard (KOS-NEXUS-020): NX-REQ-082 to NX-REQ-089 are SELECTED by NX-DEC-023 (approval of the rules), NX-REQ-090 (methodology defaults) and NX-REQ-091 (automated checks) are PROPOSED. Each cites the standard's rule categories, which are the verification baseline until the checks exist.
- NX-REQ-092 to NX-REQ-100 are the DMA controller requirements: NX-REQ-092 (a general-purpose DMA controller with 32 channels) is SELECTED by NX-DEC-025; NX-REQ-093 to NX-REQ-100 (placement, transfer types, modes, addressing, scatter-gather, arbitration, signalling and low-power operation) are PROPOSED. The owner's feature list was adapted to AXI terms; the adaptations are listed in NX-DEC-025.
- NX-REQ-101 to NX-REQ-104 are the memory architecture requirements of KOS-NEXUS-008 (part 1): NX-REQ-101 (the 40-bit application address width) is SELECTED by NX-DEC-026; NX-REQ-102 to NX-REQ-104 (access attributes per memory class, coherency and IOMMU position, unmapped and denied access) were PROPOSED defaults and are SELECTED by NX-DEC-030. NX-REQ-029 (confirmation of the width against the C910 configuration and the application masters) was OPEN and is SELECTED by NX-DEC-031.
- NX-REQ-105 to NX-REQ-108 define the boundary between the security and application domains (NX-ARCH-GAP-002): NX-REQ-105 (exactly two controlled crossings, one from the security core into one application window and one application-to-security mailbox) is SELECTED by NX-DEC-027; NX-REQ-106 to NX-REQ-108 (the boot window, the mailbox and the isolation rules) were PROPOSED and are SELECTED by NX-DEC-030, as is NX-REQ-028.
- NX-REQ-109 to NX-REQ-111 are SELECTED by NX-DEC-029, the owner's review answers on the memory architecture: the security core boot window reaches System SRAM only and never DDR4 (109), the mailbox window keeps NX-REQ-072 intact (110), and the NOR window is cacheable and read-only with program and erase only through the controller registers (111). The other parts of NX-REQ-102, NX-REQ-106, NX-REQ-107 and NX-REQ-108 were approved later by NX-DEC-030.
- NX-DEC-030 records the owner's approval of the remaining PROPOSED items of KOS-NEXUS-008, so NX-REQ-028, NX-REQ-053, NX-REQ-054, NX-REQ-102 to NX-REQ-104 and NX-REQ-106 to NX-REQ-108 are SELECTED. The approval came before the width was confirmed for every application master (AC-015); NX-DEC-031 later records the owner's confirmation for every application master, so NX-REQ-029 is SELECTED. The attachment of the crossings and the mailbox layout stay OPEN (NX-ARCH-OI-037), and the division of the peripheral register space stays OPEN (NX-ARCH-OI-036).
- NX-REQ-112 proposes the division of the application peripheral register space into the APB-0 and APB-1 windows and one window per peripheral instance or block (NX-ARCH-OI-036). It is PROPOSED, so it changes by change request until the owner selects it by a decision record; the parent region and its base and size stay SELECTED (NX-REQ-053).
- The A0 draft is imported at [../architecture/A0_INTEGRATION_DRAFT.md](../architecture/A0_INTEGRATION_DRAFT.md); NX-REQ-032 onward cite its section numbers as source. Only NX-REQ-032 (secure AXI interconnect) is SELECTED in that batch; all others are PROPOSED or OPEN. Not yet covered: the frame-pool bank and ECC organisation, key provisioning, anti-rollback, debug lifecycle and the peripheral feature details, which the draft lists as open.
